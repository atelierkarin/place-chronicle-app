# Place Chronicle（仮称）基本設計書

- 文書バージョン：0.1（初期構想）
- 作成日：2026-10-11
- 状態：開発前・方向性確定／詳細仕様は未確定
- 想定開発形態：個人・余暇を使った長期開発

## 1. プロジェクト概要

### 1.1 コンセプト
**自分の足跡を、美しく保存し、再発見する。**

訪れた施設・場所に対して、訪問日、短文の感想、写真を残し、**地図・時系列・写真**という三つの視点から閲覧できる個人向けWebサービス。初期は自分専用で利用する。継続的に使える品質が確立できたら、公開プロフィールや他ユーザーの利用を検討する。

### 1.2 解決したい課題
- 写真や感想が端末・SNS・旅行記などに分散し、場所を起点に見返しにくい。
- 同じ場所に何度も訪問した際の記録がまとまらない。
- 旅単位・施設単位・年月単位での振り返りが難しい。
- 既存の地図サービスは場所の検索や評価が中心で、自分の訪問履歴をじっくり眺める用途とは必ずしも一致しない。

### 1.3 成功条件
**MVPの完成条件（必須）**
1. 場所を登録し、緯度・経度を保持できる。
2. 同じ場所に複数の訪問記録を追加できる。
3. 訪問記録に短文と写真を紐付けられる。
4. 地図上のピンから場所・訪問記録を閲覧できる。
5. 訪問記録を日付順と場所別で閲覧できる。
6. 登録したデータと写真をバックアップ・復元できる。
7. スマートフォンでも無理なく閲覧・記録できる。

**個人的な利用定着の目標（目安）**：実際の過去の訪問10件・写真30枚を登録し、1か月後にも自分から開いて見返したくなること。

## 2. 基本方針と非目標

### 2.1 設計原則
- **個人利用を優先**：SNSの成長指標や他人の評価に開発が引っ張られない。
- **場所と訪問を分離**：一つの場所に何回でも訪問記録を追加できる。
- **データの可搬性**：将来サービスを終了しても記録を取り出せる。
- **段階的な複雑化**：小さく完成させ、必要になった機能だけ増やす。
- **写真は原本を尊重**：表示用サムネイルとは別に原本を管理する。
- **プライバシー優先**：最初の保存データは非公開を基本とする。

### 2.2 MVPでは作らないもの
- フォロー・いいね・コメント・通知
- おすすめ投稿・ランキング・広告
- 外部の施設情報の大規模自動収集
- 経路検索・乗換案内
- AIによる写真自動説明・高度な画像検索
- 複数ユーザー向け権限・課金・モデレーション機能

## 3. 利用シナリオ

1. **帰宅後の登録**：旅先で撮った写真を選択し、場所・訪問日・感想をまとめて登録する。
2. **再訪の比較**：ある旅館の施設ページから初訪問、2回目、3回目の記録を時系列で見返す。
3. **地図からの発見**：地図で過去に訪れた場所を眺め、写真と当時の感想を開く。
4. **時期別の振り返り**：「2026年10月に訪問した場所」を一覧表示する。
5. **旅行単位の整理**：任意の「旅」グループに複数の訪問記録をまとめる（MVP後に正式対応）。

## 5. 情報設計・データモデル

### 5.1 基本エンティティ

**Place（場所）**
- id: UUID
- name: string（必須）
- category: string（任意。例：温泉、旅館、飲食店、神社、公園）
- latitude / longitude: number（場所登録時は必須。緯度経度の妥当性を検証）
- address: string?（任意）
- note: text?（場所についての固定メモ）
- created_at / updated_at

**Visit（訪問）**
- id: UUID
- place_id: UUID（Placeへの参照、必須）
- visited_at: timestamp with timezone（必須。実際の訪問日の表現はUI上でローカル日付に変換）
- text: text?（感想。空欄も許容）
- created_at / updated_at

**Photo（写真）**
- id: UUID
- visit_id: UUID（Visitへの参照、必須）
- storage_key: string（保存先を識別する内部キー）
- thumbnail_key: string?
- original_filename: string
- mime_type: string
- byte_size: integer
- width / height: integer?
- caption: text?
- sort_order: integer
- created_at

**Trip（旅行）**：MVP後に追加する独立エンティティ。Visitと多対多にするか、Visitにtrip_idを付けるかは実際の利用状況を見て決定する。

### 5.2 関係
- Place 1 : N Visit
- Visit 1 : N Photo
- 同一地点・同名施設を自動で統合しない。重複候補の提示は後続課題。
- 場所の削除時には紐づく訪問・写真がある場合に明示確認し、誤削除を防ぐ。

### 5.3 データ保全
- DBと写真ファイルの整合性を保つ。画像アップロード失敗時に不完全な公開データを残さない。
- バックアップはメタデータ（JSONなど）と原本画像をセットで出力する。
- 復元可能性をテストする。エクスポートできることだけを保証としない。
- EXIF GPSなどの撮影メタデータは公開時の漏洩に注意し、必要に応じて除去する。

## 6. API初期設計（案）

| Method | Path | 用途 |
|---|---|---|
| GET | /api/places | 場所一覧・基本検索 |
| POST | /api/places | 場所作成 |
| GET | /api/places/:id | 場所詳細・訪問一覧 |
| PATCH | /api/places/:id | 場所編集 |
| DELETE | /api/places/:id | 場所削除（安全確認要） |
| GET | /api/visits | 訪問一覧（日付・場所フィルタ） |
| POST | /api/visits | 訪問作成 |
| GET | /api/visits/:id | 訪問詳細 |
| PATCH | /api/visits/:id | 訪問編集 |
| DELETE | /api/visits/:id | 訪問削除 |
| POST | /api/visits/:id/photos | 画像アップロード |
| DELETE | /api/photos/:id | 写真削除 |
| POST | /api/backups/export | バックアップ生成 |
| POST | /api/backups/import | バックアップ復元（検証・重複対策必須） |

設計メモ：リストAPIはページネーションと安定したソートを持たせる。写真アップロードは容量、形式、枚数の制限を設ける。エラー形式を統一する。バックアップAPIはローカル実行コマンドに変更する可能性もある。

## 7. 画面構成（初期）

1. **ホーム／地図**：訪問地点を俯瞰。クリックで場所詳細。
2. **タイムライン**：訪問日順のカード。写真・場所・感想を表示。
3. **場所詳細**：場所の情報、訪問回数、訪問記録を時系列で表示。
4. **訪問編集**：場所選択、訪問日時、本文、画像の登録・並べ替え。
5. **設定／データ管理**：バックアップ、復元、データ容量など。

後続で写真専用アルバムと旅行グループ画面を増やす。

## 8. 技術構成（暫定）

- Frontend：React + TypeScript + Vite
- Backend：TypeScript + Hono（Node.js実行）
- DB：PostgreSQL（個人利用でも、将来の拡張とSQL習熟を優先）
- 地図描画：MapLibre GL JS（地図タイルは別途選定。利用規約・負荷制限に従う）
- 画像保存：開発初期はローカルファイル。公開時はオブジェクトストレージを再検討
- 開発：Docker Compose、Git
- テスト：Vitest（ロジックとAPI）、Playwright（主要操作）

**補足**：技術スタックは拘束条件ではない。個人用途ならSQLiteから開始する選択肢もあり、運用の簡単さとPostgreSQLの練習価値を比較して決める。

## 9. 非機能要件

- **性能**：自分の数千件程度の訪問・写真から開始。地図は表示領域に応じた取得・クラスタリングを検討。
- **操作性**：スマートフォンの画面幅を重視。帰宅後に短時間で登録できるUI。
- **信頼性**：削除確認、アップロード失敗への復帰、バックアップと復元テスト。
- **安全性**：初期はローカル利用を想定。外部公開する場合は認証・認可、レート制限、画像検証、監査、プライバシー管理を設計してから公開する。
- **費用**：開発中はローカル中心。クラウドの継続費用を発生させる前に必要性を確認。
- **可搬性**：場所・訪問・写真のデータを特定サービスから取り出せるようにする。

## 10. 開発マイルストーン

### M0：土台と仕様の確認
- リポジトリ作成、開発環境、DB、テスト基盤
- 最小データモデルとAPI契約を決定
- 仮データ10件で画面の雰囲気を検証

### M1：記録できる
- 場所CRUD／訪問CRUD／写真アップロード
- 最低限の入力フォームと場所詳細
- **完了判定**：自分の訪問10件と写真30枚を登録できる

### M2：見返せる（MVP）
- 地図ビュー／タイムライン／年月・場所検索
- バックアップ・復元
- モバイル画面対応
- **完了判定**：過去の訪問を地図・日付・場所の3方向から迷わず探せる

### M3：整理が楽しくなる
- 写真アルバム、旅行グループ、タグ
- 再訪回数、訪問間隔などの可視化
- **完了判定**：過去記録を自分で見返す習慣が生まれる

### M4：任意の公開準備
- 多ユーザー化に必要な認証・権限
- 公開/非公開設定、画像のメタデータ処理
- 運用・モデレーション・費用モデルの検討
- **完了判定**：他人に見られて困る情報を公開せずに試験運用できる

※期間は固定しない。趣味の余暇開発として、フェーズ単位で完成させる。

## 11. リスク・検討事項

| リスク／未決事項 | 初期方針 |
|---|---|
| 地図タイルのライセンス・利用上限 | タイル提供元を別途選び、規約確認。無制限の無料利用を前提にしない |
| 地名の表記揺れ、同一施設の重複 | 手動登録を基本とし、後で重複候補の提示を追加 |
| 写真容量の増加 | 原本／サムネイルを分離し、容量と保存先を把握 |
| 位置情報のプライバシー | 初期非公開、公開する場合は地点の丸め・非表示も検討 |
| SNS化による運用負担 | フォロー等は後回し、まず個人サービスを完成 |
| 長期間開発の中断 | 各フェーズで動く状態を保ち、READMEと次の一手を更新 |

## 12. 次に取り組む最小タスク

1. 作業用リポジトリを作り、本設計書を `docs/design.md` として格納する。
2. Place / Visit / Photo の3テーブルのスキーマを定義する。
3. 最初に登録する実際の訪問記録を10件選ぶ。
4. `POST /api/places` と `POST /api/visits` を実装し、テストを書く。
5. まずは1件の訪問を画面に表示する。

## 13. 将来の差別化仮説

**レビューSNSではなく、場所に積み重なる個人の記憶を主役にする。**

一般的な施設評価・チェックインとの違いは「自分の再訪」「時間経過による変化」「地図・時系列・写真の連携」に重点を置くこと。差別化が実際に成立するかは、個人として使い続けて確かめる。既存サービスに類似機能がある可能性は排除しない。
